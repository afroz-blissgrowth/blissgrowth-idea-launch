# Idea Launch: Phase 2 review

Reviewer: Opus quality review, 2026-10-21. Scope: `/iv-people`, `/iv-tier`, `/iv-enrich-verify`, `/iv-activity`, `/iv-phones`, `/iv-ready`, the new and changed library modules, `bin/` scripts, workflow scripts and live workflows, tests, skills, the edited `engine/vendor/activity-checker/build_workflow_v21.py`.

## Verdict: PASS WITH FIXES

Phase 2 is well built and faithful to the plan and the Decisions. Seven defects were fixed in place (none needed a workflow change). Tests went from 92 to 96, all passing (`python3 -I engine/tests/run_tests.py`). The open items are judgement calls. One of them costs real credits (item A, phone reveal charges again for people already enriched) and should be decided before the first full run. Nothing blocks Phase 3.

## What was checked

- **Plan and Decisions.** Caps T1 5 / T2 3 in `config.json` (`brief.people.caps` overrides through one helper), applied after tiering, with title priority limiting the tiering pool to 10 per company. No credit caps or gates: dry runs only report expected credits, real cost is logged from Apollo's `credits_consumed`. Tiering follows the qualify pattern: samples of 10, the user reviews, 2 clean rounds, the lock is tied to the prompt hash, `--force` only on the user's say-so, simulated rounds are labelled. HeyReach-only v1: nothing in Phase 2 launches anything. The Mansi call sheet (`7 Ready: Calls`) is T1 only (`channels_for` adds `call` only for T1 with a phone). Anyone can run it: config lives in files, secrets in `.env` / `config.local.json`, new sheets are shared with the blissgrowth.com domain on create (`sheet.share`), and `sheet_tool.py share` covers older sheets.
- **Apollo against the current docs** (docs.apollo.io bulk people enrichment, read 2026-10-21). `mixed_people/api_search`: one company per call through `organization_ids[]`, titles plus a seniority union, `include_similar_titles`, 0 credits, per-org ledger, stops cleanly at the hourly floor. `people/bulk_match`: at most 10 `details` per call, `reveal_personal_emails`, `reveal_phone_number` and `webhook_url` go in the query string and the body is `{details}`, which is correct. `reveal_phone_number` needs `webhook_url` and the code enforces that. Credits: 1 for demographics or email, plus 8 per mobile, 0 when nothing is found. The code logs `credits_consumed` from the synchronous answer and the phone part from the webhook payload. Unmatched entries come back as `null`, but the docs do not promise input order (fixed, item 1). `request_id` is a signed 64-bit integer and is kept as a string, which is correct. On the test run Apollo charged 1 credit per person even when no email came back (15 people, 15 credits, 9 emails).
- **MillionVerifier against the docs and live.** `GET https://api.millionverifier.com/api/v3?api=&email=&timeout=` (timeout 2 to 60 s, 20 used) with a browser User-Agent. The client was run against MillionVerifier's free demo keys (no credits): `ok`, `invalid`/`no_mailbox`, `catch_all`, `disposable` parse correctly. "Apikey not found" and "Insufficient credits" are fatal. "IP address blocked" was not fatal (fixed, item 2). Only `ok` passes, `catch_all` is kept and marked for a second verifier, `unknown`/`invalid`/`disposable` fail, `error` is retried. Results are cached per email and the key never reaches logs (tested).
- **List quality port** against `list-quality-scorecard/scripts/score-list.ts`. The 8 dimensions, weights (2, 1, 1, 1.5, 1, 1, 2, 1), formulas for duplicates (100 - 20 x %), bad titles (100 - 10 x %) and catch-all density (<5% good, linear to 15%), and the A+ to F grade bands all match. The deliberate adaptations are documented in `lib/quality.py`: strict `ok` only, domain limit = T1 cap + T2 cap instead of the original "average under 2", ICP fit = share at qualify `keep` (review counts half), and MV `catch_all` added to the role list. All are sensible for this engine.
- **Activity checker contract** (live, read-only). `NrweLKOV7gMu54bD` is **INACTIVE**. Its triggers are Webhook, Manual and Execute Workflow, with no schedule, so switching it on starts nothing by itself. Compared with the pre-patch backup, only the Config node differs: four added lines, validated, with marker `IL_CONTRACT_V1`. Connections are identical and settings are preserved (`executionOrder`, `callerPolicy`, `binaryMode`). The same lines are in `build_workflow_v21.py`. In `run_activity` the `finally` always deactivates, after errors and interrupts too, except on a timeout, where the checker stays on and is marked `activated_by_us` so that `--resume` collects and then switches it off. A checker that someone else had switched on is left on. All of this is covered by tests.
- **Phone receiver** (live). `kSDGLbA4yZvk5Q9d` is active with three nodes (Webhook on a secret path, Flatten, data table insert). Data table `YCCl3AOviLQDC54i` has 6 rows: 5 real ones from the test and the fake `TESTPID1` row. The real payload shape (`status, request_id, people[{id, status, phone_numbers[{raw_number, sanitized_number, type_cd}]}]`) matches `parse_row`. The bridge `WyIsq2lNqJEudsuv` is active.
- **Idempotency.** Search uses the per-org ledger plus person-id dedupe. Tier results are append-only and a batch file is ingested once per mtime. Enrich never re-sends `matched`/`no_match`, MV is cached per email, activity is cached per profile, phones are never re-requested once `requested`. The people sheet and Ready tabs push only changed rows (hashes), and rows are never deleted (`withdrawn`).
- **Secrets.** The `.env` keys are never printed. The bridge secret and the phone webhook path are in `config.local.json` (gitignored, chmod 600). Error messages strip the MV key.
- **Schema migration.** The bridge `add_columns` action plus `ensure_schema` run before every People and Ready push. They only append columns, never reorder or rename.
- **READY semantics.** The stage registry derives status from files, and READY needs every stage done or skipped and a non-test run. Summary line 1 of the test run correctly says NOT READY.
- **Skills.** The six new SKILL.md files are short, name the exact commands, state the user-decision points (titles, tier review, skips) and give the gotchas. A new teammate can follow them. No em dashes anywhere in the code, docs or skills.

Template them into a copy library file per channel and step, with the reply rates next to them, then draft V1 plus variants per tier into "8 Copy". Follow the project rules: no links and no filler in first messages, no em dashes. Tune with the user on samples, the same way as qualify and tier. The GrowthEngine frameworks are MIT, so keep attribution in NOTICE.md.
2. **Reply-agent idea page.** Create the idea's page in the **Blissgrowth** Notion workspace (project `notion` MCP, not claude.ai Notion) under "Idea Contexts", built from `memo.md` and `brief.json`: ICP, tiers, offer, objections, call-to-action. Store the page URL in the run folder, so the step is idempotent and the stage can be registered.
3. **/iv-launch.** Create the HeyReach campaign as a DRAFT (or only a lead list when draft creation is not available). Use the `5 Ready: LinkedIn` rows split by tier with the approved copy, and get an explicit user approval before creating anything. Never start the campaign. `7 Ready: Calls` already is Mansi's T1 call sheet: add an idempotent share with her and a calls status column. Smartlead stays out of v1.
4. **/iv-run orchestrator.** Walk `stages.REGISTRY` in order, calling each skill's script. Stop only at the user-decision points: the brief, qualify and tier tuning reviews, and the campaign approval. There are no credit gates, but always show the dry-run estimate. Use `run_in_background` for people search and the activity check, and resume from `summary.md`. Decide issue A before the first full run.
5. Replace the volume guesses in `config.json` with rates measured on the first full run, and compare `apollo-usage.jsonl` with Apollo's usage stats.
