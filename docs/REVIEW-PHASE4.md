## What was checked

- **Intent fidelity.** `/iv-brief` step 13 is a one-question-at-a-time signals interview with a menu of total employees, engineers, operations and the other Apollo departments, plus text signals. It asks for a threshold in plain numbers and uses the hard/soft test ("would you still reach out?"). It reads the list back and states the cost. Fixed: the skill only offered signals "the memo gives a reason for", so with a silent memo the three headcounts Afroz named might never be asked (item 5). Pilot sizes are 10 to 20 (default 15). Sizes outside that range are refused in the brief and at `start`. The exclusions cover garden leave, retired, career break, role ended, between roles and Open to Work.
- **Apollo bulk_enrich against the docs.** The docs say: `POST /api/v1/organizations/bulk_enrich`, `domains[]` in the query (a `details` body is also allowed now), up to 10 per call, 1 credit per organization. The response carries `organizations[]`, `missing_records` and `departmental_head_count`. The client matches all of this (`apollo.org_bulk_enrich`, `body={}`, `domains[]` query). It reads `credits_consumed` when present, else it counts matched organizations. The TEST run logged 10 credits for 10 matched domains. Live data: every record has all 19 department keys, zeros included, and they match `signals.known_departments`, including Apollo's own spelling `media_and_commmunication`. So `missing_department_is_zero` almost never fires in practice. Pairing does not assume the answer keeps the input order (by domain, then position only when the lengths agree). `apollo.request` with GET puts the params in the query string and sends no body, which is correct for `organizations/enrich`.
- **Threshold logic.** A hard rule drops a company only on a known value (`evaluate` returns `unknown` when the record is missing or not_found, or the employee estimate is missing for `_pct`). For a ratio with 0 or missing employees the result is unknown. All ops, aliases and `between` are validated, and a text signal can never be hard. Hard drops happen before the model (`auto-signal`), the row is kept, the drop is never used as a tuning sample, and ingest never overwrites it. A changed threshold releases the row for re-scoring. The brief hash excludes signals, so changing a threshold does not force `--accept-brief-change`.
- **Qualify prompt.** The four `MANDATORY BLOCK` markers are untouched and still enforced by `check_prompt`. The signals section is appended after them and before the output contract. A prompt without signals is byte-identical to before.
- **Pilot state machine.** not_started, selected, enriched, scored, awaiting_review, reviewed, approved, plus skipped, stale, simulated and legacy. Every state comes from `pilot/` files.
  - Approval is bound to `review_hash` and the pilot size, so changing a mark reopens the gate (tested). A blank sheet cell never erases a chat mark (`merge_sheet_rows`). Blank local marks are never pushed over sheet marks (`people.push_to_sheet` pops blank `pilot_review`/`pilot_note`, and `sync_accounts_sheet` only sends set values).
  - Legacy: a full ledger, or `accounts.csv` with no ledger, counts as legacy. A limit ledger does not, so a limit test pull is not legacy (tested). For people, the gate is legacy only when enrichment already happened and no pilot was drawn.
  - Spec drift after approval (`spec_sha`) is recorded but does not invalidate the approval. This is a sensible judgement call because the pilot is about the review, not the prompt (open D).
- **Spend gates.** `accounts_pull.py` (full pull) and `enrich_verify.py enrich` refuse unless the gate is approved, skipped, disabled or legacy (a dry run always works). Rejected pilot people get `pilot_rejected` and are never enriched, sent to the checker or revealed for phones. While the accounts pilot is open, qualify works on the pilot accounts only. Fixed: `signals_run.py run` without `--scope` could enrich every account in `accounts.csv` while the pilot was open (item 4).
- **Simulated approvals.** `record --simulated` and `approve --simulated` are refused on a non-TEST brief. An approval that includes simulated rows is itself simulated. On a real brief it maps to state `simulated` (partial), so the gate stays closed. Seeds are tagged "yes (SIMULATED)".
- **Exclusions.** These are recomputed from files in `people.build_rows`, so the run is idempotent and rows are never deleted. An excluded person has empty `channels`. Missing data never excludes. Keyword matching uses word boundaries ("Head of Retirement Products" passes). The builder's narrowing of the bare words "seeking", "looking for", "former" and "ex-" is sensible and configurable (config groups, `re:` regexes, per-source switches). Three false-positive gaps were fixed (items 1 to 3).
- **Sheet migration.** The column order in `ACCOUNT_COLS` (base, qualify, signals, pilot) matches how `add_columns` appends. The live TEST sheet headers of "2 Accounts" and "4 People" match `schema` exactly, and the data rows line up.
- **/iv-run.** The registry order is brief, pilot_accounts, accounts, signals, qualify, people, tier, pilot_people, enrich_verify and so on. The gate kind is set by `pilot.next_action`: auto for pull, signals and request-review; claude for qualify on the pilot; user for review and approval. The driver stops at both gates. The `stalled` check depends on the state text changing, and every auto gate step changes the state, so a step that changes nothing stops as stalled.
- **SKILL.md usability.** The skills are clear, give exact commands, say who decides, and say that only the user can skip a gate. No em dashes, and Blissgrowth is spelt correctly.
- **Tests.** 95 Phase 4 tests with fakes cover every op, unknown data, the endpoint shape, the cache, batches, hard drops, the prompt blocks, every gate state, simulated, stale and legacy approvals, sheet merges, script refusals, orchestrator stops and keyword guards. The new tests are all offline.
